## 一、结论：还缺 6 个 P0 闭环、11 个 P1 闭环

**一句话**：ZW-Insight 在**经营分析与资金治理的"深度"上明显强于竞品**（滚动预测、风险台账、应收台账、票据/融资/工资专户、资金日报都是竞品没有的）；但缺的是**"对称性"与"闭环最后一公里"**——应收有台账而应付没有、付款侧勾稽有联动而回款侧没有、资金调拨有表有流程却没有接口。

## 二、P0 缺口详析（6 个）

### G1 在途额度占用缺失 ★最实质

| | 竞品 | ZW-Insight |
|---|---|---|
| 占用模型 | **四段**：`订单金额 / 已申请 / 申请中 / 可申请` | **两段**：`可付上限 = cumulative_settlement + 净奖惩 − cumulative_paid` |
| 在途是否占用 | **是**（"申请中"单列并计入扣减） | **否**——`cumulative_paid` 仅在**审批通过**时累加，SUBMITTED 期间不占 |
| 复用范围 | 付款侧 + **开票侧**（已开票/开票中/可开票） | 无 |

**证据**：竞品明细表头（`07` 卷 §6.2 ⑥⑩）；ZW `PaymentApplyService.validatePaymentLimit`（行 532-546）、`ContractPayableMapper.sumPayableOutstanding`。

**后果**：同一合同下可并发提交多张付款申请，每张单独校验时都通过（因为已付未变），**合计可超付**。工程审计高频问题。
**建议**：`biz_payment_apply` 增加在途占用查询（`status IN (SUBMITTED)` 求和），校验式改为 `已申请 + 申请中 + 本次 ≤ 可付上限`；同一组件复用到开票。

### G2 应付台账缺失 ★对称性缺口

| 维度 | 应收（有） | 应付（缺） |
|---|---|---|
| 台账实体 | `biz_receivable` | **无** |
| 生成 | 结算审批通过自动生成（幂等） | — |
| 核销 | `biz_receivable_write_off` FIFO 核销明细 | **无** |
| 账龄 | `NOT_DUE/D0_30/D31_60/D61_90/OVER_90` | **无** |
| 双写不变量 | `biz_project.receivable_amount` = OPEN 余额合计（同事务） | **无** |
| 现有替代 | — | 散落两个 Mapper 求和：`ContractPayableMapper.sumPayableOutstanding`、`BizPaymentApplyMapper.sumApprovedUnpaidRemaining` |

**证据**：ZW `ReceivableService` / `ReceivableController`（`/page`、`/aging`、`/drill/{id}`）；应付侧无 `biz_payable` 实体。
**后果**：应付无账龄、无核销追溯、无单一事实源；`cockpit/overview` 的 `payableOutstanding` 是实时求和而非台账，**无法审计**。
**建议**：建 `biz_payable` + `biz_payable_write_off`，口径对齐应收（含账龄桶与项目双写不变量）。这是本卷**最推荐优先做的一项**——收益高、模式已被应收验证、风险低。

### G3 资金调拨功能未闭环

**证据（ZW）**：`BizFundTransfer` + `fund_transfer_approval.bpmn20.xml` 存在，但 `FundTransferService` **无任何 REST Controller**（仅被 `BusinessDetailService` 映射为 `FUND_TRANSFER`）；`submit`（行 82-101）**提交即置 APPROVED 并回写**，审批回调未接线。
**后果**：调拨单无法从界面发起；即便发起也不走审批。
**建议**：补 Controller + 接线审批回调；补"调拨事由"必填校验（竞品为必填 `调拨事由*`）。

### G4 回款侧勾稽无联动（收付不对称）

**证据（ZW）**：`BankFlowService.matchFlow`（行 245-247）勾稽 `PAYMENT_APPLY` 时调 `refreshPayStatus` 重算三档；勾稽 `PAYMENT_RECEIVED` **无任何联动**。
**后果**：付款侧"现金口径"完整，收款侧"现金口径"缺失 → 双口径只在支出侧成立。
**建议**：为 `BizPaymentReceived` 增加 `receiveStatus`（未到账/已到账）与勾稽回写，使双口径在收付两侧对称。

### G5 无统一支付出口

**证据**：竞品 `/fun/payment/list?payStatus=!PAID`（页签 待付/已付/支付流水，跨单据类型，统一"去支付"）；ZW 全仓检索"统一支付/支付中心/待付清单/payCenter"**无命中**，最接近的是只读聚合 `FundPlanService.futureExpenseTop`。
**后果**：出纳需在各单据列表间切换、逐单 mark-paid；无"今日待付汇总"作业视图。
**建议**：新增"待付资金池"聚合（跨付款申请/报销/薪资/其他支出），支持批量标记已支付。

### G6 无关联收付无法登记

**证据**：竞品 `unRelatedPay`（无关联付款）与 `unRelatedCollection`（无关联收款）**单列统计**；ZW 收款 `contractId` 可空（有"若为预收款，请清空关联合同"提示）但**无"无关联"标记与统计**；付款 `contract_id NOT NULL`（`00_schema.sql:2018`）**硬禁止无合同付款**。
**后果**：现实中的"无合同付款"（押金、零星采购、代垫）无法入账，只能挂假合同或走其他支出。
**建议**：放开付款的合同必填约束（或增加"无关联"类型）+ 双侧增加无关联统计口径。

## 三、P1 缺口详析（11 个，择要）

### G7/G8 客户维度与三维台账

竞品 `客户账款` 页：16 指标（(合同+签证)金额/收入合同/收入签证/合同收款/产值金额/产值未收/收入合同结算/合同结算未收/(合同+签证)未收/开票申请/销项发票/销项税额/收款登记/发票未收/未返还保证金/还款金额），行是客户、列是指标。
ZW：**无客户/甲方聚合接口**（全仓无客户维度分析），供应商聚合仅 3 指标（`contractAmount/settlementTotal/paidTotal`）且按项目×类别。
**建议**：抽象"主体×指标"横向台账组件，先落客户维度（甲方回款是老板第一关切）。

### G9 全公司合同执行汇总

竞品 `/analyse/contract/execute/total`：16 指标 × 收入/支出，含 `unRecordAmount`（未收/未付）。
ZW `ContractStatisticsController.amount-summary`：**`projectId` 必填**，只出单项目；**签证统计未发现**。
**建议**：增加全公司汇总端点（复用现有累计字段）。

### G10 资金构成分析

竞品 8 个资金看板页，每页含"构成饼图 + 月度折线"（如付款登记：合同付款 99.35% / **无关联付款 0.65%**；收款登记：工程收入 69.63% / 项目筹备金 30.37% / 银行结息；薪资发放三维构成）。
ZW：**未发现**该维度（只有 `top-expenses` 按科目聚合 + `gap-attribution` 按项目/收款方归因）。
**建议**：按 `paymentCategory`/`receiveCategory` 出构成饼图与月度趋势；薪资侧按"自有/分包 × 按人/按组 × 工资/生活费"三维（ZW 已有 `labor` 薪资统计基础）。

### G11 成本分析趋势与来源构成

ZW `ProjectCostControlDTO.trends` 在 `getCostControl` 中**硬编码为 `new ArrayList<>()`**——数据（CBS 流水）齐备但接口未实现；无来源饼图；`CostTotals` 只有 `actualTotal`，**无 paidTotal**（即 G19）。
**建议**：实现 trends（复用 `biz_cost_account_txn` 按月聚合）+ 来源构成（复用 `sourceType`）+ 补 `paidTotal`。

### G12 借款单/还款单

竞品 `JKD`/`HKD` 独立单据，还款单含 `还款总金额` 与 `普通还款金额`，加载时调 `/repayment/amount` 查可还额。
ZW：**未发现**独立借款单（只有 `biz_reserve_fund_apply` 备用金 + `BizReserveFundReturn`）；`biz_personal_reimbursement` **无冲抵字段**（项目报销有）。
**建议**：补借款单或扩展备用金语义；个人报销补冲抵。

### G13/G14 发票链

竞品：开票申请(55) → 销项发票(57) 字段同构（"要开"→"已开"）；进项发票(56) 挂支出合同 + **采购订单四段占用**。
ZW：`biz_invoice_apply`（销项）与 `biz_invoice_received`（进项）**无外键、无来源字段**；进项发票与采购订单**无额度占用**。
**建议**：加 `source_invoice_apply_id`；进项发票补订单可开票额度校验。

### G15 余额调整单

竞品有（`调整方向`=调增/调减、`调整原因*`、审批 84）；ZW **未发现**（余额变动只靠流水登记与调拨回写）。
**建议**：补余额调整单（账实不符的合规留痕入口）。

### G16 账户级授权 / 私户

竞品：账户表单含 `授权人员*` + `授权角色`，且「账号一旦被选用，将无法修改」；账户类型含**公户/私户**。
ZW：`biz_bank_account.account_type = BASIC/GENERAL/SPECIAL`（基本/一般/专用）；**无授权字段、无私户**；有账户分组（司库多级树）。
**建议**：补账户级授权（谁能用哪个账户）+ 私户类型（工程私卡普遍存在）。

### G17 多合同付款申请

竞品有"多合同付款申请"；ZW `contract_id` 单值 NOT NULL。
**建议**：付款申请加明细子表（contractId + amount），兼容单合同现状。

### G18 工程量-材料-损耗联动

竞品产值统计 14 列含 `图纸计量 / 累计工程量 / 累计产值 / 累计材料使用量 / 现场存货 / 累计材料损耗率`。
ZW：有 `biz_quantity_list`/`biz_boq_item`/`biz_bom_item`（工程量清单/BOQ/BOM）与 `biz_project_material_stock`（收发存），但**未发现**两者联动的统计端点，库存分析**无损耗率**。
**建议**：建"工程量→材料用量→损耗"台账（这是材料成本管控的关键，也是 ZW 材料模块的空白）。

### G19 项目 360 的实付成本维度

竞品 `实际成本` 卡（`totalCost`/`profitRate`）与 `实付成本` 卡（`totalPaidCost`/`cashProfitRate`）**同屏并列**，实测利润率 17.3% vs 现金利润率 84.2%。
ZW：`CockpitController./fund-ratios` 有支付率双口径（`paymentRate` vs `cashPaymentRate`），但**成本侧只有权责口径**（`CostTotals.actualTotal`，无 paidTotal）；`ProjectCostControlDTO` 亦无 paid 对应项。
**建议**：成本控制 DTO 补 `paidTotal`/`cashCostRate`，与竞品双卡并列对齐。

| A7 | **利润快照 + 利润归因 + 环比** | `biz_profit_snapshot` + `attributeProfitChange` + `changes{...}` | 有双口径卡片，**无快照/归因** |
| A8 | **双口径口径文档化 + 不变量** | `docs/资金流转全景图.md`（6 条不变量）+ `AGENTS.md` | **双口径实现存在但无口径文档**，实测存在跨层口径不一致 |
| A9 | **单据穿透下钻** | `DrillDownService`（成本类别→供应商→合同→原始单据）、应收 8 级下钻 | 有 `/analyse/*` 但**无逐层穿透** |
| A10 | **月度经营分析（10 类 × 6 列）** | `biz_monthly_operation_analysis` + `MonthlyAnalysisTask` | 有 64 列项目台账（更宽，但**无月度落库快照**） |

> **对照结论**：ZW 在 **A1–A4**（预测、风险、应收、勾稽）四项上构成**机制级领先**；竞品在**采购寻源**（多轮竞价/密封报价）与**分析层宽度**（64 列台账、三维分析、资金构成图）上领先。**两者互补，不是替代关系。**

## 五、设计取舍差异（非缺口，需业务判断）

| 差异 | 竞品做法 | ZW 做法 | 判断 |
|---|---|---|---|
| **付款登记** | 独立单据 `FKDJ`（可审计凭证） | **无独立单据**，支付态内嵌 `pay_status` + 银行流水勾稽 | ZW 更"事实驱动"（支付是银行事实不是单据），但**缺独立凭证**；建议保留现设计，同时用"支付流水"视图补凭证感 |
| **额度占用基准** | **按采购订单**（订单四段） | **按合同**（结算−已付） | 竞品颗粒更细；ZW 按合同对分包/劳务更自然。**建议双轨**：采购类按订单、服务类按合同 |
| **余额与流水关系** | 余额手工快照，无恒等 | 同样手工快照 + 余额调节表 | 双方均未做恒等；ZW 有调节表略优 |
| **资金调拨方向** | 调出/调入**账户** | 调出/调入**项目**（+账户） | 竞品偏账户维度，ZW 偏项目维度；建议两者都支持 |
| **账户类型** | 公户/私户（资金性质） | 基本/一般/专用（账户用途） | 两个维度正交，**建议都建**（性质 + 用途） |
| **审批覆盖面** | 账户开立/到账/支付/筹备**不审批**；调拨/余额调整**审批** | 付款/报销/备用金/开票/结算/调拨等**均走 BPMN** | ZW 更严；但"资金到账/支付"若不审批，操作风险高，**ZW 保持现状更稳** |

## 八、一句话总结

**本项目不缺"深度"，缺"对称"与"最后一公里"。** 应收有台账而应付没有、付款有勾稽联动而回款没有、调拨有表有流程而没有接口、成本有权责口径而没有现金口径——这四处不对称是最高性价比的补齐点；而**竞品的 64 列经营台账与三维主体分析**则提示本项目在**分析层宽度**上还有系统性空间。

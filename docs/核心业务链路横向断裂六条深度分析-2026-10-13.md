## 摘要

6 条断裂**表面各异、病根只有三个**：

| 病根 | 命中的断裂 | 本质 |
|---|---|---|
| **① 缺"可被代码读取"的关联键** | X1、X3、X6 | 系统建了"结构树"（工程量清单 / WBS / 合同）与"执行流水"（材料出库 / 进度计划 / 收票），中间**没有外键、或外键只写不读、或表单根本不提交** |
| **② 跨模块零联动（各自闭环）** | X2、X4、X6 | 模块内部自洽，跨模块靠人工在系统外对账；劳务↔财务、合同↔发票双向零引用 |
| **③ 事件契约不全 + 系统任务上下文缺失** | X4、X5 | 变更事件契约缺 `contractId` 且无合同侧消费者；Outbox 派发线程未标"系统任务"，被数据权限拦截器抛异常 |

**严重度分级**（对业务数据的影响方式）：

| 级别 | 含义 | 断裂 |
|---|---|---|
| **A 静默失效**（数据错/不更新，用户无感知） | 最危险 | **X4**（合同变更额永不回写）、**X5**（CBS 传导 100% 崩溃且只剩类名） |
| **B 能力缺失**（该功能压根不存在） | 功能空缺 | **X1**（材料无法按工程量归因）、**X2**（无考勤源、工资单与专户不联通） |
| **C 死字段/死入口**（有结构但走不通） | 隐性空转 | **X3**（`wbs_node_id` 只写不读）、**X6**（收票表单无合同字段 + 只回写一张表） |

## X4 变更事件 ↔ 合同累计变更额

### 一句话结论
变更事件批准后，合同 `cumulative_change_amount` **绝不会被回写**——事件契约 `ChangeEventApprovedEvent` 不含 `contractId`，`BizChangeEvent` 也无合同外键，且**全仓不存在"合同侧"事件消费者**；唯一能写这个字段的是 `ChangeVisaService.onApproved`（变更签证链路）。javadoc 声称的"合同累计变更金额回写处理器"是**失实声称**。

### 现状机制
- **字段只在施工合同上**：`zw-contract/.../domain/BizConstructionContract.java:92` `private BigDecimal cumulativeChangeAmount;`（DB `00_schema.sql:703`）。其它合同实体无此字段。
- **全部写入点**（grep `setCumulativeChangeAmount`）：
  1. `ConstructionContractService.java:117-118` —— 创建时仅初始化 0；
  2. `ChangeVisaService.java:104-108` —— **唯一真实累加**（读-改-写）；
  3. **无任何 ChangeEvent 路径**；`BizConstructionContractMapper` 只有 `addCumulativeOutput` / `addCumulativeOutputWithinLimit` / `addCumulativeInvoiceAmount`，**没有 `addCumulativeChangeAmount`**。
- **事件契约缺字段**：`zw-common/.../event/contract/ChangeEventApprovedEvent.java:31-61` 字段全表 = `schemaVersion / eventId / eventNumber / projectId / tenantId / costDelta / scheduleDelayDays / affectedAccounts / affectedWbsIds / approvedAt / approvedBy`——**无 `contractId`**；生产方 `ChangeEventService.buildApprovedPayload:467-495` 也不设它。
- **消费者只有一个**：全仓 `implements OutboxEventHandler` 的生产实现**仅** `zw-budget/.../handler/ChangeEventApprovedCostHandler.java`（只动 CBS）；**zw-contract 侧零消费者**。

### 断点
| 断点 | 位置 |
|---|---|
| 契约无 `contractId` | `ChangeEventApprovedEvent.java:31-61`；`buildApprovedPayload` `ChangeEventService.java:467-495` |
| 无合同侧处理器 | 全仓 `implements OutboxEventHandler` 仅命中 budget 一个（复核：`grep -rln "implements OutboxEventHandler"` = `ChangeEventApprovedCostHandler` + 测试） |
| 失实 javadoc（3 处） | `ChangeEventService.java:307-313`、`ChangeEventApprovedCostHandler.java:20-29`（ASCII 图明确画了"合同累计变更金额回写（zw-contract 侧处理器）"分支）、`ChangeEventEvents.java:31-36` |

### 后果
产值上限判定式 `合同额 + 累计变更额` 读的是 `cumulativeChangeAmount`，它只反映**变更签证**、不反映**变更事件**：
- `OutputReportService.java:274`（`validateOutputLimit`）、`BizConstructionContractMapper.addCumulativeOutputWithinLimit`（SQL guard）、`ContractStatisticsService.java:64`、`CockpitService.java:638` 同口径。
- ⇒ 变更事件批的额度**永不抬高产值上限**，产值上报会被误拦/误放，走变更事件的钱成为"孤岛"。

### 修法
1. `ChangeEventApprovedEvent` 增可空 `Long contractId`（遵守其"字段只增不删、新增可空"约束，`:22-24`）。
2. `biz_change_event` 增列 `contract_id`（双轨迁移：`zw-app/.../db/migration/Vxxxx__*.sql` + `deploy/db-init/NN_Vxxxx__*.sql`），`BizChangeEvent` 加字段、`buildApprovedPayload` 赋值。
3. 新增 `ChangeEventApprovedContractHandler implements OutboxEventHandler<ChangeEventApprovedEvent>`，按 `contractId` 累加。**必须自带幂等**（Outbox 至少一次，金额累加非幂等）——建议 `(eventId, contractId)` 唯一键台账 + 原子 SQL。
4. ⚠ 新处理器若用 `BizConstructionContractMapper.selectById/updateById`，会踩与 **X5 完全相同的**"无用户上下文 → 数据权限拦截"坑（该 Mapper 类级 `@DataPermission`），须与 X5 一起修。
5. 删除/修正 3 处失实 javadoc。

### 不确定项
未找到"曾经存在后被删掉的合同侧处理器"痕迹（无残留类/注释/测试）；`biz_change_event.contract_id` 是否曾在历史迁移中存在后被删——未逐一比对全部历史 SQL。

## X5 变更事件 ↔ CBS 潜在成本

### 一句话结论
批准后事件经 Outbox **只调 CBS `current_amount`（增量）**，既无 commitment/forecast 也无"潜在成本（Pending Cost Change）"中间态；**且这条传导在生产上必然崩溃**：Outbox 调度线程只设 `tenantId`、不设 `userId` 也不标系统任务，处理器首次读 `@DataPermission` 的 `BizCostAccountMapper` 即抛 `DataPermissionException`，被 MyBatis 包成 **message 为 null** 的 `MyBatisSystemException` → Outbox 永远 PENDING/DEAD，CBS 永不更新、无流水。

### 现状机制
- 批准 → 投递：`ChangeEventService.approve:315-336` → `outboxRecorder.record(TYPE_APPROVED, …)`。
- 派发：`zw-common/.../event/outbox/OutboxDispatcher.java` `@Scheduled poll()` → `deliver` → `invokeHandler` → `binding.handler().handle(message)`；`deliver` **只回填租户**（`:171 SecurityContextHolder.setTenantId(...)`），**不标系统任务、不设 userId**（复核确认：该文件无 `markSystemTask`/`setUserId`）。
- 唯一消费者：`zw-budget/.../handler/ChangeEventApprovedCostHandler.handle:75-152` → 组 `PostCommand(accountId, AMT_CURRENT, …)` → `costLedgerService.postBatch(commands):149`。
- `CostLedgerService.postBatch:234-246` → `post` → `applyDelta:283-294` → `case AMT_CURRENT -> costAccountMapper.adjustCurrentAmount(...)`：**只动 `current_amount`**，不碰 commitment/actual/forecast，也不写"潜在成本"。
- **无"潜在成本"中间态**：grep `PENDING_COST|pendingCost|potentialCost|PendingChange|未决变更|潜在` 在 Java 源码**零命中**。

### 断点（崩溃点，已定位到代码级）
崩溃点在处理器**首次读库**：`ChangeEventApprovedCostHandler.java:119`
```java
BizCostAccount account = costAccountMapper.selectById(delta.getAccountId());
```
`BizCostAccountMapper` 带**类级** `@DataPermission`（`zw-budget/.../mapper/BizCostAccountMapper.java:22-24`）：
```java
@DataPermission(value = {
    @DataColumn(projectColumn = "project_id", userColumn = "created_by", deptColumn = "dept_id")
})
```
链路：
1. `selectById` → `DataPermissionInnerInterceptor` → `ZwDataPermissionHandler.getSqlSegment`；
2. `:57` 先查 `isSystemTask()` —— **Outbox 线程从未调用 `markSystemTask()`**（复核：全仓调用者仅 `SecurityContextHolder` / `SystemEventPublisher` / `MonthlyAnalysisTask` / `UrgeNotifyEventListener` / `TenantTaskRunner` / `WorkflowBootstrapRunner`，**OutboxDispatcher 不在其中**）→ 返回 false，不豁免；
3. 命中类级注解 → 取 `userId`（调度线程为 null）→ **抛 `DataPermissionException("无法获取用户上下文…")`**；
4. 该 `RuntimeException` 被 `DefaultSqlSession` 包成 `PersistenceException` → `MyBatisExceptionTranslator` 翻译失败 → `new MyBatisSystemException(e)`；
5. **`MyBatisSystemException.getMessage()` 恒为 null**（`UncategorizedDataAccessException.<init>(null, cause)`）→ `OutboxDispatcher.java:183-190` 落库 `last_error = "MyBatisSystemException"`（与线上观测一致），重试 5 次后 DEAD。

> **为何单测不报警**：`ChangeEventApprovedCostHandlerTest` 用 Mockito `mock` 了 `costAccountMapper`，拦截器根本不执行 → 单测全绿、生产必崩。

### 后果
`sys_outbox_event` 中 `CHANGE_EVENT_APPROVED` 恒 PENDING→DEAD；`biz_cost_account.current_amount` 不变；`biz_cost_account_txn` 无流水。变更事件对预算的传导 **100% 静默失效**，且 `last_error` 只剩类名、栈被吞，可诊断性差。未批准的变更也无任何"潜在成本"可见性 → 预算/预测失真。

### 修法
1. **根因（最小改动）**：`OutboxDispatcher.deliver` 调 `invokeHandler` 前 `SecurityContextHolder.markSystemTask()`，`finally` 还原，与 `TenantTaskRunner` 的系统任务豁免语义一致 → `ZwDataPermissionHandler:57` 直接放行。
2. 备选：让 handler/`CostLedgerService` 的读走 `@InterceptorIgnore(dataPermission="true")` 专用通道（不如系统任务标记统一）。
3. 可诊断性：`handleFailure` 落库的 `last_error` 改存**根因消息**（`e.getCause()` 链）而非类名。
4. 补集成测试（真拦截器 + `tenant_id=9999`）覆盖"Outbox 派发 → CBS 记账"端到端；现有单测因 mock mapper 无法发现此类问题。
5. 业务补全：引入"潜在成本"中间态（批准前 `costDelta` 计入 forecast/独立字段，批准后转 current）。

### 不确定项
只读考古、未实机复现；`MyBatisSystemException` 完整运行时栈日志中不可得（`getMessage()==null` 是"线上只剩类名"的直接原因，已由字节码验证，但未抓到线上实际栈）。`CostLedgerService.post` 内 `:152/:169` 的 `selectById` 同样会崩，但 handler `:119` 是执行路径上**第一个** DB 访问，必先崩于此。

## X1 材料 ↔ 工程量

### 一句话结论
材料收发存与工程量清单之间**没有任何关联列、也没有任何联动代码**：出库只扣库存、不校验 BOQ 限额；产值上报只回写 `biz_boq_item.completed_quantity`、从不碰材料；材料成本当前甚至**不进入 CBS 归集**（取的是采购结算金额）。

### 现状机制
- **两张"工程量"表**（复核字段）：
  - `BizQuantityList`（`zw-contract/.../domain/BizQuantityList.java:21-56`）：`projectId / contractId / itemName / specification / unit / quantity / unitPrice / amount`——**无 `completedQuantity`**，全仓无写回逻辑；
  - `BizBoqItem`（`.../domain/BizBoqItem.java:19-49`）：**有 `completedQuantity`**（`:43`）。
- **产值回写只命中 BOQ**：`OutputReportService.onApproved:176-182` 遍历明细调 `boqItemMapper.addCompletedQuantity(...)`；底层 `BizBoqItemMapper.java:30-32` `UPDATE biz_boq_item SET completed_quantity = COALESCE(completed_quantity,0)+#{quantity} WHERE id=#{id} AND deleted=0`。删除时对称冲销同样只冲 BOQ。
- **出库表无关联列**（复核）：`BizMaterialOutboundDetail`（`:19-34`）= `outboundId / materialName / specification / unit / quantity / unitPrice`；主表 `BizMaterialOutbound`（`:21-39`）= `projectId / outboundType / outboundDate / operatorName / contractId / returnType / status`——**均无 `boqItemId` / `quantityListId` / `wbsNodeId`**。
- **出库只校验库存**：`MaterialOutboundService.save:71-95` 全程只对 `biz_project_material_stock` 做 `deductStock`（`:91`），**无任何 BOQ/工程量/限额读取**。
- **材料成本不进 CBS**：`CostRollUpService.rollup:138-146` 材料 ACTUAL 取 `biz_purchase_settlement.settlement_amount`（`CostRollUpMapper` 无材料出库查询，复核 0 命中），归集口径是**金额**、无数量维度。

### 断点
| 断点 | 位置 |
|---|---|
| 出库明细/主表无 BOQ/WBS 外键 | `BizMaterialOutboundDetail.java:19-34`、`BizMaterialOutbound.java:21-39` |
| 出库不校验工程量限额 | `MaterialOutboundService.java:71-95`（仅 `deductStock:91`） |
| 产值回写只覆盖 BOQ，`biz_quantity_list` 无字段可承接 | `OutputReportService.java:176-182`、`BizQuantityList.java:21-56` |
| 材料成本不进 CBS（按金额取采购结算） | `CostRollUpService.java:138-146` + `CostRollUpMapper`（0 命中材料出库） |

### 后果
1. **材料成本无法按工程量归因**：出库单只到"项目 + 材料名"，系统算不出"单方工程量材料耗量 / 材料损耗率"，**限额领料拦截不存在**；
2. **无法做"工程量-材料"勾稽**：BOQ `completed_quantity` 与材料出库量分属两套账、无键相连，无法交叉验证"完成 1000m³ 却领 3000m³"；
3. **材料成本与 CBS 材料账户脱节**：只反映"采购结算额"（钱花在采购），不反映"现场实际消耗"（料用在哪）；无法按 `biz_cost_account.wbs_node_id` 把材料成本摊到 WBS 工作包。
4. 附带：`CostRollUpService.java:36` 类头 javadoc（"ACTUAL = 已审批结算 + 材料出库消耗"）与 L138 代码（已把材料出库作为双计项剔除）**自相矛盾**。

### 修法
1. **加关联列**：`biz_material_outbound_detail` 增 `boq_item_id BIGINT NULL`（或 `wbs_node_id`），双轨幂等迁移。
2. **出库校验升级**：若 `boqItemId != null`，查 BOQ 累加已领量做"限额领料"比对（至少预警不阻断，超限抛 `BusinessException`→409）。
3. **CBS 归集补材料维度**：`CostRollUpMapper` 增 `listMaterialOutboundConsumptions(projectId)`（APPROVED + `outbound_type=PICK`，金额 = `Σ quantity×unit_price`）。⚠ **须先定口径**：与"采购结算"同时计入会双计（AGENTS.md 旧表述已被 PI-4 推翻），需人工决策"二选一"还是"采购结算=承诺、材料出库=实际"。
4. 同步修 `CostRollUpService.java:36` / `CostRollUpMapper` 的口径注释。

### 不确定项
`biz_quantity_list` 与 `biz_boq_item` 是两套并存清单（前者按项目+合同、无层级；后者按合同、有层级与 `completed_quantity`），前端实际用哪张未逐页确认。材料出库 `quantity×unit_price` 是否即"消耗成本"取决于 `unit_price` 是入库价还是标准价（`BizMaterialOutboundDetail.unitPrice` 无注释）。

## X3 进度 ↔ WBS

### 一句话结论
两棵树**完全并行**：`biz_schedule_plan` 上有一个可选外键 `wbs_node_id`（V2026_96 新增），前端能写入，但**后端没有任何代码读取它做汇总**，`ProjectWbsNodeService` 与 `SchedulePlanService` **零互调**——这是一个"只写不读"的单向引用，实质等于两棵孤立的树。

### 现状机制
- **`wbsNodeId` 的写入方**：前端 `zw-insight-web/src/views/site/schedule.vue:78-82` 的 WBS 选择器（`clearable`，可不选）→ `createSchedule/updateSchedule` → `ScheduleController.savePlan/updatePlan` → `SchedulePlanService.save/update:130-162` → `planMapper.insert/updateById`。
- **读取方：无**（复核）：`grep wbsNodeId|wbs_node_id` 于 `zw-site` **仅命中实体字段声明本身**（`BizSchedulePlan.java:29`）；`BizSchedulePlanMapper` 是空 `BaseMapper`。
- **两模块零互调**（复核）：`site→Wbs` 0 命中；`project→SchedulePlan` 0 命中。
- **WBS 无进度字段**：`BizProjectWbsNode.java:45-52` 只有 `startDate / endDate / status`（`status` 是启用/停用/关闭的**生命周期态**，非进度态）——**无 `progress`**。
- **进度 `progress` 来源**：`ScheduleFeedbackService.syncPlan:112-135`（人工进度反馈 → 回写 `biz_schedule_plan.progress` → 仅在该树内 `calculateParentProgress` 向上汇总），**不向 WBS 传播**。

### 断点
| 断点 | 位置 |
|---|---|
| WBS 无进度字段 | `BizProjectWbsNode.java:45-52` |
| 进度→WBS 回写调用缺失 | `ScheduleFeedbackService.syncPlan:112-135`、`SchedulePlanService.calculateParentProgress:186-224`（无 `wbsNodeId` 分支） |
| WBS→进度读取缺失 | `ProjectWbsNodeService`（全类零 schedule 引用） |
| `wbs_node_id` 只写不读 | `BizSchedulePlan.java:29` + 空 `BizSchedulePlanMapper` |

### 后果
1. **无法按 WBS 工作包回答"进度到哪了"**：WBS 承载成本侧结构（CBS 账户挂 `wbs_node_id`、变更事件挂 `affected_wbs_ids`），但无进度字段、无从进度计划汇总的代码——用户在 WBS 工作包上**看不到任何进度百分比**；
2. **"成本-进度对账"名存实亡**：`wbs_node_id` 存进库但没有一行代码拿它 JOIN 成本与进度，实体注释"为成本-进度对账铺路"**当前是死字段**；既算不出"某工作包花了多少成本、进度完成多少"，也算不出挣值（EV/PV/AC）；
3. **进度与范围解耦致口径分裂**：同一"工作包"在两棵树上需人工两次录入且无一致性校验，必然漂移。

### 修法
1. WBS 加 `progress` 字段**或**查询时按 `wbs_node_id` 聚合子进度计划派生（参照 `SchedulePlanService.markDelayed` 的"派生态"既有模式，避免落库与人工维护冲突）。
2. 补"进度→WBS"汇总：`ScheduleFeedbackService.syncPlan` 之后若 `plan.getWbsNodeId()!=null` 触发 WBS 汇总。**依赖方向**：site→project 已成立（site 已 import `BizProjectMapper`），可直连；若需 project→site 必须走 `zw-common` 事件（AGENTS.md §10）。
3. 前端补一致性：WBS 管理页显示该节点下挂接的进度任务及汇总进度。

### 不确定项
`biz_schedule_plan.wbs_node_id` 是否在 BI/报表 SQL 中被消费（本次仅扫 server/web/deploy）；若有外部消费方，结论"只写不读"需收窄为"应用内只写不读"。`BizProjectWbsNode.status` 的 `ACTIVE-进行中` 注释语义含糊，是否被前端当进度展示未逐页确认。

## X2 劳务 ↔ 考勤 ↔ 工资专户

### 一句话结论
**两者都有，且是两条彼此独立的断链**：① 全仓**不存在任何"考勤/工时实体"**（`考勤` 零命中），工资单只汇总"派工单"，而派工单工时是**手工填写**；② 劳务域与财务域之间**零代码引用**（双向 grep 均空），工资单审批通过只改自身状态、**完全不触发**工资专户代发；专户代发金额由页面**手工输入**、无代发明细表。

### 现状机制
- **工资单金额来自工单汇总**（复核）：`LaborPayrollService.save:107-124` 按"项目+班组+周期+已审批"捞 `biz_work_order`，`totalSettlement = Σ workOrder.totalAmount`，`totalPaid` 恒置 0。
- **工单金额 = 工时×时薪 + 加班工时×加班费率**（复核）：`WorkOrderService.calculateTotalAmount:168-175`；`BizWorkOrder.hours/hourlyRate/overtime/overtimeRate` 均前端录入，**无打卡/考勤来源**。
- **无考勤实体**：`grep 考勤`=0、`grep manhour`=0；唯一"出勤"语义是**统计时从工单派生**（`SalaryStatisticsServiceImpl.java:494-507`：出勤天数=工单日期去重计数、加班工时=工单 `overtime` 求和）。
- **专户代发是手工台账**：`WageSpecialAccountService.recordWagePayment:108-123` 入参 `amount` 直传，只更新专户两个汇总字段、**不写任何明细行**（`payDate` 参数甚至未被使用）；入口 `WageSpecialAccountController.java:62-69`（`@RequestParam`）、前端 `finance/wage-account/index.vue:118-119` 为 `el-input-number` **手工输入**。
- **跨模块零引用**（复核）：`grep com.zwinsight.labor` 于 zw-finance = 0；`grep com.zwinsight.finance` 于 zw-labor = 0。
- **工资单审批不触发专户**：`LaborPayrollService.onApproved:189-191` 仅 `setStatus("APPROVED")`；`LaborApprovalListener.java:62-66` 无"触发专户代发"分支。

### 断点
| # | 断点 | 位置 |
|---|---|---|
| B1 | 无考勤数据源，工时为手工录入 | `考勤` grep=0；`WorkOrderService.java:168-175` |
| B2 | 工资单金额只汇总工单、不引用考勤 | `LaborPayrollService.java:119-124` |
| B3 | 工资单审批不触发专户代发 | `LaborPayrollService.java:189-191`、`LaborApprovalListener.java:62-66` |
| B4 | 两模块零引用 | 双向 import grep 均 0 |
| B5 | 专户代发金额手工输入、无代发明细 | `WageSpecialAccountController.java:62-69`、`wage-account/index.vue:118-119`、`WageSpecialAccountService.java:108-123` |

### 后果
1. **"总包代发"沦为对账孤岛**：财务手工敲一个数就记"代发"，无法与工资单/工单/班组/工人逐笔对应，**审计时无法证明"专户资金仅用于本项目农民工工资"**（724 号令第 31 条要求可追溯）；
2. **工资单金额与真实考勤脱钩**：工时人工填报，全链无实名考勤背书，存在虚报工时合规风险；
3. **到位率/合规判定失真**：`arrivalRate = totalReceived / wageBudget`，而 `wageBudget` 是建户手填预算、`workerCount` 是手工值，均不随合同/花名册变化；
4. 两套"农民工工资"数据（劳务域工资单 / 财务域代发台账）永不交叉，靠人工在系统外对账。

### 修法
1. **补代发明细表**（最关键）：`biz_wage_payment_detail`（`account_id/payroll_id/worker_id/amount/pay_date/batch_no`），`recordWagePayment` 改按工资单明细批量代发，主表 `totalPaid` 由明细汇总。
2. **打通审批回调**：`LaborPayrollService.onApproved` 经 Spring 事件（契约放 `zw-common`，遵 AGENTS.md §10）发布 `LaborPayrollApprovedEvent`，财务域监听器据此**自动生成/预填代发单**（金额 = 工资单 `totalSettlement`）。
3. **建考勤源（推荐）**：`biz_labor_attendance`（工人/日期/出勤工时/来源），工单 `hours` 默认取自考勤，统计的"出勤天数"改读考勤表。
4. 专户 `wageBudget` 从劳务/人工费合同或预算带出，`workerCount` 由花名册实时统计。

### 不确定项
`biz_wage_special_account.workerCount` 是否有写入方（倾向仅建户时前端传入）；`biz_labor_payroll.total_paid` 是否有非零来源（`SalaryStatisticsServiceImpl.java:102-104` 注释提示存在未在本次范围内的"工资支付链"）；`recordWagePayment` 是否有定时任务调用（仅见 Controller 一处入口）。

## X6 收票 ↔ 合同开票额

### 一句话结论
**三层断点叠加**：① 收票表单**根本没有合同选择器**（`contractId` 从不提交，回写分支永远进不去）；② 即便有 `contractId`，后端 `InvoiceReceivedService` **只回写 `biz_other_contract` 一张表**；③ 采购/支出合同虽有开票列但**无人回写**，劳务/机械/分包合同**连开票列都没有**。

### 现状机制
- **后端只回写 `biz_other_contract`**（复核）：`InvoiceReceivedService.java:59-66` 注入的写回 Mapper **仅 `BizOtherContractMapper`**（`:27`）；`delete:88-92` 对称回冲同样只针对该表。
- **对照销项侧**：`InvoiceApplyService.onApproved:199` 回写的是**施工合同** `contractMapper.addCumulativeInvoiceAmount(...)`。
- **各合同开票列盘点**（复核）：

| 合同表 | 开票字段 | 是否被回写 |
|---|---|---|
| 施工 `biz_construction_contract` | `cumulativeInvoiceAmount` | ✅ 销项：`InvoiceApplyService.java:199` |
| 其他 `biz_other_contract` | `cumulativeInvoice` | ✅ 收票：`InvoiceReceivedService.java:64`（**唯一**） |
| 采购 `biz_purchase_contract` | `cumulativeInvoiceReceived` | ❌ 仅建单置 0（`PurchaseContractService.java:113`） |
| 支出 `biz_expense_contract` | `cumulativeInvoiceReceived` | ❌ 无任何写入方 |
| 劳务 / 机械 / 分包 | **无该列**（复核 `cumulativeInvoice` 字段数 = 0） | ❌ |

- **前端无合同字段**（复核）：`finance/invoice-received.vue` 模板（`:74-97`）只有 项目/供应商/发票金额/税率/收票日期；`formData`（`:129-135`）**无 `contractId`**；提交 `:188` 直接 `createInvoiceReceived(formData.value)` → 后端 `if (contractId != null)` **永远为 false**。移动端 `types.ts:224-230` 同样无该字段（页面注释却写着"有 contractId 时"）。

### 断点
| # | 断点 | 位置 |
|---|---|---|
| C1 | 收票表单无合同关联字段，`contractId` 从不提交 | `invoice-received.vue:74-97` / `:129-135` / `:188`；`types.ts:224-230` |
| C2 | 后端只回写 `biz_other_contract` | `InvoiceReceivedService.java:59-66`（注入 Mapper 仅 `BizOtherContractMapper:27`） |
| C3 | 采购/支出合同有开票列但无人回写 | `PurchaseContractService.java:113`（仅置 0）；`BizExpenseContract` 无 setter |
| C4 | 劳务/机械/分包合同无开票列 | `BizLaborContract` / `BizMachineContract` / `BizSubcontract` 均无 |

### 后果
1. **收票数据完全悬空**：`biz_invoice_received` 只记"项目+供应商+金额"，`contractId/contractCategory/supplierId` 全空，无法回答"这张进项票对应哪份采购/支出合同"；
2. **合同"累计收票"长期为 0 或脏值**：采购、支出合同的 `cumulative_invoice_received` 永远 0，无法算"合同收票率/待收票余额"，也无法驱动付款前置校验（"未足额收票不得付款"）；
3. **唯一被回写的 `biz_other_contract` 通路在界面上也断了**（C1），只有直接调 API 传 `contractId` 才生效；
4. **劳务/机械/分包合同无收票口径**，进项票只能散落在"其他合同"里，合同类型与发票归属错位。

### 修法
1. **前端补合同选择器**（最小改动、最高收益）：按 `projectId` 联动合同下拉，选择后带出 `contractCategory`/`supplierId`，一并提交；移动端同步。
2. **后端按 `contractCategory` 分派回写**：`InvoiceReceivedService.save/delete` 路由到施工/采购/支出/劳务/机械/分包各自累计字段（先给劳务/机械/分包补 `cumulative_invoice_received` 列，双轨幂等迁移）。
3. **统一字段命名**：当前施工叫 `cumulative_invoice_amount`、其他叫 `cumulative_invoice`、采购/支出叫 `cumulative_invoice_received`——语义混乱易错配，建议统一。
4. 收票登记增"合同+发票号"唯一性校验，防重复回写。

### 不确定项
`biz_invoice_received` 是否还有除 Controller `POST` 外的写入入口（批量导入/定时任务）；历史数据 `contract_id` 填充率（需连库统计）；`InvoiceSummaryService` 是否触碰合同累计字段；前端菜单是否真的暴露 `invoice-received.vue`。

## 七、交叉结论：六条断裂的共同病根

**X1、X3、X6 是同一种病**——系统建了"结构树"（工程量清单 / WBS / 合同）与"执行流水"（材料出库 / 进度计划 / 收票），但**中间缺少可被代码读取的关联键**：
- X1：连关联列都没有（出库明细无 BOQ/WBS 外键）；
- X3：列有了（`wbs_node_id`），但**没有读取方**、且 WBS 无进度字段可承接；
- X6：后端回写通道单一（只认 other_contract），且**前端表单根本不提交 `contractId`**。

**X2、X4 是同一种病**——**模块各自闭环，跨模块靠人工**：劳务↔财务双向零引用、合同↔发票双向零引用、变更事件↔合同无消费者。

**X4、X5 是同一种病**——**事件契约不全 + 系统任务上下文缺失**：契约缺 `contractId`（X4）、Outbox 线程未标系统任务被数据权限拦死（X5）。二者叠加使"变更事件"这条跨模块链**在合同侧不存在、在成本侧崩溃**。

**一句话**：主干（合同→预算→执行→成本→资金→关闭）在**模块内部**是自洽的，但**模块之间没有"单一事实源"**——同一件事（工程量、进度、工资、变更额、发票）在系统里被记了两遍或多遍，彼此不校验、不联动。这正是 `feature-ledger` 里 42% 页面停在 L1 单路径 CRUD 的根因。

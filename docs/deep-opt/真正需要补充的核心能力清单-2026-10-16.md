# ZW-Insight 真正需要补充的核心能力清单

> 复核日期：2026-10-16
> 结论性质：竞品二次对比 + 本仓九模块读码 + 三路独立复核 + 行业规范校准；**未改代码、未运行、未连库**
> 判断标准：仅当能力同时满足「施工企业高频真实场景」「影响金额/税务/合同真实性」「现有能力不能等价解决」「补后能形成闭环」「有可靠数据基础」时，才列为核心
> 竞品证据中的【推想】公式、特定光伏 EPC 字段、单租户配置，不进入通用需求基线

---

## 一、最终结论

真正需要补的不是竞品的 66 字段、8 段口径、大宽表，也不是另建一张「合同执行单」。

**应补 5 项核心业务能力，并先修 3 项正确性问题。**

核心业务主链应是：

```text
合同计价与支付约定
  → 工程计量（产值/工程量/变更/签证/索赔）
  → 过程结算（分节点确认无争议价款）
  → 应收/应付
  → 销项/进项发票
  → 收款/付款/银行流水
  → 权责成本、现金流、利润分析
```

这条链有行业依据：财政部、住建部财建〔2022〕183 号明确，施工过程可按时间或进度节点，对已完成且无争议的工程量（含变更、签证、索赔）进行计算、确认和支付；已确认的过程结算文件纳入竣工结算，原则上不重复审核。国家税务总局 2024 年第 11 号公告又明确数电发票全要素、红冲、用途确认、入账标识与查验。故核心不是复制竞品页面，而是补齐**过程结算事实链 + 发票事实链**。

## 二、先修 3 项正确性问题（不是新增功能）

### F1. 预算控制必须真正闭环

**现状**：
- 劳务合同 `save` 有 `@BudgetCheck(category="LABOR")`，但 `submit` 只启动审批，不复核预算；草稿改额后可绕过保存时校验（`LaborContractService:51-95`）。
- 预算 WARN 的 `sendWarningNotification` 仅 `log.warn`，没有真实站内信（`BudgetControlConfigService:353-362`）。

**必须补**：
1. 所有受控合同在 `submit` 时按当前金额重新校验预算；不能只在 save 校验。
2. WARN 走 `UrgeNotifyEvent` 等现有真实通知链，收件人取有效 `PROJECT_MANAGER`；无收件人应明确 FAILED，不伪造成功。
3. BLOCK/WARN/EXEMPT 的结果写入可审计日志，保留项目、科目、预算额、已占用额、本次金额、执行率、模式。

**为什么是核心**：预算控制是系统已有承诺，当前只是链路不完整；这比新增任何看板更优先。

### F2. 签证与变更事件必须只有一个财务生效源

**现状**：
- `ChangeVisaService:103-109` 已用状态 CAS + 原子 `addCumulativeChangeAmount`，旧稿所称「读后写静默丢失」已过期，不再是缺陷。
- 但签证审批和变更事件 Outbox 都能累加合同 `cumulative_change_amount`；二者没有业务级关联或唯一守卫。同一事项若重复录入，会重复抬高动态合同额、产值额度和利润。

**必须补**：
1. 产品规则明确：变更事件是上游事实、签证是价款确认，还是二者互斥二选一。
2. 推荐：`change_visa.change_event_id` 可选关联；有关联时仅签证审批作为财务生效点，变更事件只做影响评估/CBS 传导；无关联的独立签证仍可生效。
3. DB 唯一 guard 防同一变更事件挂多个有效签证；已生效后禁止重绑。
4. 审计能从合同累计变更额下钻到唯一来源单据。

**为什么是核心**：这是金额单一事实源问题，直接影响合同额度和利润，非竞品功能补齐。

### F3. 修正税务指标的虚假语义

**现状**：`DashboardService:835-863` 的 `taxDifference` 用的是 `Σ销项发票金额 − Σ进项发票金额`，不是税额差，却命名为 tax difference。

**必须补**：
- 在销项发票事实台账落地前，将其改名为 `invoiceAmountDifference`，禁止显示为「应交增值税」。
- 不得用开票申请的派生税额冒充实际销项税额。

**为什么是核心**：错误指标比缺指标更危险。

## 三、5 项真正需要补充的核心业务能力

### C1. 过程结算：打通收入侧最关键断点（最高优先级）

**真实痛点**：施工企业不是竣工时才结一次。按月、形象进度、里程碑确认工程量，变更/签证/索赔同步进入当期结算，才是进度款、应收、开票的合法依据。

**现有不足**：
- 产值上报有 BOQ 明细与审批回写，但它表达「完成了多少」，不等于双方确认的「无争议应结价款」。
- `biz_final_settlement` 只有末端一次性结算，字段薄，且不回写施工合同累计结算额。
- 收入合同因此没有 `cumulative_settlement`，回款率也缺少「收款/结算额」。

**最小闭环**：
1. 新增收入合同过程结算单（或把现有 final settlement 扩展为 `PROCESS/FINAL` 两种模式），支持月度/节点结算。
2. 来源必须是已审批产值明细、变更签证、索赔/奖罚，逐项选择；保存来源 ID、申报金额、审定金额、争议金额、核减原因。
3. 结算单包含：本期完成工程款、已确认变更/签证/索赔、预付款扣回、质保金扣留、其他扣款、应付进度款、累计已结算。
4. 审批通过原子回写合同 `cumulative_settlement`；来源项只能被有效结算一次，作废/驳回/删除须释放占用。
5. 生成/更新应收台账；开票申请上限以「累计产值」还是「累计已结算」为租户可配置规则，不静默改变现有行为。
6. 竣工结算引用并汇总已确认过程结算，原则上不重复审核，只处理尾差和争议项。
7. 全链可下钻：合同 → 计量 → 过程结算 → 应收 → 开票 → 回款。

**为何不建竞品式合同执行单**：我们已有产值、入库、结算、CBS 承诺成本；再建执行单会重复事实源。真正缺的是**双方确认的过程结算**。

### C2. 合同计价与支付条款结构化

**真实痛点**：预付款、进度款、质保金、支付比例、扣回方式、支付期限决定每期应收/应付，不能只靠备注或资金计划外置表达。

**现有不足**：施工合同无结构化 `receiptTerm`，无收款节点；部分支出合同仅有自由文本 `payment_terms`。资金计划存在，但不是合同义务来源。

**最小闭环**：
1. 合同计价方式：固定总价/固定单价/可调价，风险范围和调价规则。
2. 收付款节点：预付款、进度款、竣工款、质保金；每节点记录触发条件、计划日期、比例/金额、扣回规则、宽限期。
3. 过程结算/付款申请/应收预测引用节点，不复制金额；节点达成由业务单据驱动。
4. 质保金按合同约定自动计提到现有 `biz_retention_money`，返还审批与收款登记/应收核销贯通。
5. 合同修订时对节点前后快照留痕；已发生节点不得无痕覆盖。
6. 不照搬竞品【推想】子表字段，以现有资金计划与质保金表为基础，避免第二套计划。

**价值**：使预测、结算、付款、质保金都有合同依据，而非凭人工记忆。

### C3. 税务事实链：支出合同税额 + 销项台账 + 进销项查验

**真实痛点**：发票申请不等于真实发票；合同含税结构、实际开票/收票、红冲、用途确认、查验必须分层。数电发票已全国推行，票面包括金额、税率、税额、价税合计等全要素，且有红冲、用途确认、查验流程。

**现有不足**：
- 四类主支出合同缺 `tax_rate/amount_without_tax/tax_amount`，只有其他合同有。
- 开票侧只有 `biz_invoice_apply`，无真实销项发票台账（票号、实际开票日期、蓝/红字、红冲关系、查验/入账状态）。
- 进项发票已有身份唯一 guard 和税额三件套，但无查验状态/用途确认。
- 当前 `taxDifference` 不是税额差。

**最小闭环**：
1. 四类主支出合同补含税、不含税、税率、税额；历史税率未知保持 NULL，禁止猜填。
2. 新建销项发票事实台账，与开票申请一对多关联；记录数电票号码、实际开票日、票种、蓝/红字、原票、金额、税率、税额、价税合计、查验状态、入账状态、附件指纹。
3. 进项发票补查验/用途/入账状态；查验结果需记录来源、时间、操作人，不能把“人工核对”冒充税务平台查验。
4. 合同累计开票口径明确：继续按审批申请，还是按实际销项发票；迁移前不得破坏 R7 现有勾稽。
5. 基于真实票据事实计算：销项税、可抵扣进项税、红冲影响、税额差；不直接命名为「应交税」时须写明估算口径。
6. 已付款未收票先做**金额敞口**；待合同/发票税率完整后再给税额影响，禁止直接称「税负损失」。

### C4. 材料分批结算的价格差异与审批留痕

**真实痛点**：入库价与最终结算价因调价、数量折扣、质量扣款、运费、税率变化而不同，强制取入库价会让结算无法贴合现实。

**现有不足**：分批结算已具备来源入库行、可结算余量、审批中占用与退货扣减，但 `PurchaseSettlementService:206-208` 强制用入库 `unitPrice` 重算，不能合理调整。

**最小闭环**：
1. 明细保留 `sourceUnitPrice`、`settlementUnitPrice`、`priceDifference`、`differenceReason`、附件。
2. 项目/租户可配置容差（绝对值/百分比）；容差内自动通过，超容差必须填写原因并提升审批或指定角色会签。
3. 后端在保存、提交、审批生效前均重新计算，前端数值不可信。
4. 累计结算仍只由 APPROVED 明细汇总，保持 R7 不变量；作废/驳回释放占用。
5. 价差能下钻到来源入库行、采购合同、审批记录。

**边界**：竞品只实测到 UI 标签/文案，服务端硬拦未证实；本能力成立是因为我们现有强制入库价确实不支持真实结算场景，不是因为竞品有。

### C5. 成本归集覆盖与经营口径治理

**真实痛点**：管理工资、点工、劳务分包工资等若不进入 CBS，人工成本和利润会失真；同一成本若劳务结算与工资发放双计，也会失真。

**现有不足**：CBS 仅归集四类合同承诺与四类结算实际，薪资发放未接入；不能直接旁路记流水，因为每日 Rollup 会按绝对目标校正，且可能与劳务结算双计。

**最小闭环**：
1. 先定成本政策：工资属于劳务结算明细、独立人工成本，还是仅现金子口径；按企业/项目可配置但每个来源只能落一个事实口径。
2. 若工资独立入实际成本，必须纳入 `CostRollUpMapper` 的 target 绝对值计算与幂等流水，不能旁路改余额。
3. 建立来源类型排重：工资单、劳务结算、点工单之间一对一/汇总关联；存在关联时只归集一次。
4. CBS 下钻补完整来源信息（业务单号、日期、经办人、来源明细），不新增竞品式“人工核实”按钮；异常走差异处置/修复单。
5. 经营指标统一输出 `value + numerator + denominator + basis + asOf`，先补项目级：
   - 收款/合同额、收款/产值、收款/过程结算、收款/实际开票；
   - 权责成本、现金支出（明确不称成本）、预测完工成本；
   - 产值毛利、结算毛利、预测利润（仅在成本基础完整时显示）。
6. 无 CBS、无过程结算、无实际发票时返回不可算/缺数据原因，不用 0 冒充。

**为什么不是“复制双成本双利润率”**：现金支出不是会计成本；竞品的现金利润率公式属【推想】。我们需要的是**口径治理与可信派生指标**，不是再造一套成本账。

## 四、有条件做，但不是当前核心

| 能力 | 判定 | 触发条件 |
|---|---|---|
| 付款/开票在途金额展示 | 可实时聚合 `SUBMITTED`，无需持久化 `payingAmount`；属体验优化 | 用户确有并发申请误判困扰时 |
| 多合同付款申请 | 需主从表、分摊、撤销、部分支付、跨收款方、银行勾稽重构 | 真实客户有集中付款场景且频次高时 |
| 项目/供应商/业主经营台账 | 做精简只读聚合，不做 64 列宽表 | C1-C5 事实链稳定后 |
| 合同闭合状态 | 应由过程结算/票款/附件归档证据自动判定，可配置 | C1-C3 完成后 |
| 成本异常确认/差异处置 | 可做异常工单，不做无语义的“已核实”按钮 | 自动对账发现需人工处置的差异后 |
| 材料损耗分析 | 需图纸量、定额用量、发货/库存可靠数据 | 特定 EPC/材料管控客户提出时 |
| 索赔管理 | 行业上属过程结算组成，但本轮未核现有实现 | 下一轮单独核实后纳入 C1 |

## 五、明确不做

1. **不把五张支出合同物理合并成一张表。** 统一模型是竞品实现选择，不是业务能力；跨类型统计用只读 UNION/聚合层。
2. **不新增竞品式合同执行单。** 我们已有产值、入库、结算和承诺成本；新增执行单会形成重复事实源。用 C1 过程结算补真正缺口。
3. **不照搬项目 64 列、供应商 25 列、客户 16 列大宽表。** 先保证事实链正确，再按角色提供少量可下钻指标。
4. **不持久化 `payingAmount` 只为展示。** 审批中金额可实时聚合；要做硬冻结则另立并发额度专项。
5. **不做竞品式成本人工核实按钮。** CBS 已有幂等流水、`balance_after` 恒等守卫和每日对账；需要的是异常处置，不是人工背书。
6. **不按竞品【推想】公式实现材料损耗率、双利润率、额度硬拦或合同子表。**
7. **不先做纯看板再补事实链。** 无过程结算、实际销项发票、完整成本来源时，漂亮指标只会放大假精确。

## 六、实施顺序

### 阶段 0：正确性修复

F1 预算控制闭环 → F2 签证/变更单一财务生效源 → F3 税务指标改名止损。

### 阶段 1：合同到结算事实链

C1 过程结算 → C2 结构化合同支付条款。两项必须协同设计，否则过程结算没有合同节点依据。

### 阶段 2：票税与材料支出闭环

C3 税务事实链 → C4 材料结算价差机制。

### 阶段 3：成本与经营口径

C5 薪资等成本来源纳入 Rollup + 统一指标元数据；最后才做经营看板/台账。

## 八、证据边界

- 本轮未运行、未复现、未连双机数据库；正确性问题仍需测试证明。
- 竞品运行时只读数据证明字段/接口存在，不证明服务端全部校验和公式。
- C1/C2 的行业必要性主要来自官方价款结算规则，而非竞品。
- C3 的必要性主要来自数电发票全流程规则与本项目事实台账缺口。
- C4/C5 来自本项目代码无法覆盖的真实业务边界，不依赖竞品推想。

## 二、差异管理原则

1. **允许有差异，但差异必须可追溯、可复现、可回滚。** 可形成差异的范围包括：功能开关、租户模块、`.env` 非敏感配置语义、菜单与权限、角色与数据范围、字典、BPMN、定时任务配置、预设/演示数据，以及经明确设计的客户专属功能。
2. **默认共享代码，不默认共享运行效果。** 当前 `main` 普通 push 默认向 `server1 + server2` 部署同一构建产物；但数据库配置、流程定义和业务数据相互独立，故一机验证通过不代表另一机通过。
3. **禁止服务器本地形成不可追踪代码分叉。** 不得只在某台服务器手改 jar、前端 dist、容器内文件或源码。分机功能应优先由仓库内代码配合显式配置、租户模块或 feature flag 实现。若必须使用不同构建产物，须先让 CI/CD 明确支持目标产物及回滚路径，并在本台账登记。
4. **Schema 迁移与预设数据分开治理。** 结构迁移原则上兼容并应用于两机；仅某一环境需要的预设数据不得混入无目标守卫的公共初始化。目标专属数据脚本须幂等，写明目标企业/机构、适用租户、前置探针、备份与回滚方式。
5. **不以“另一机已有”为依据直接复制。** 菜单、角色、BPMN、字典和种子数据导入前，先只读核对目标机现状与业务需要；不得为消除审计 WARN 而向客户环境强灌演示数据。
6. **不记录秘密。** 台账可记配置键名与行为差异，不得写密码、Token、私钥、验证码或完整个人敏感信息。

## 六、变更与验收流程

### 变更前

1. 确认目标是 `server1`、`server2` 还是双机，并核对 IP、容器、数据库和企业/机构。
2. 读取本台账，判断是新增差异、修改既有差异，还是消除差异。
3. 对数据库写操作先做只读探查与目标表备份；脚本须幂等，并具有不会命中另一企业/租户的显式守卫。
4. 在第四节新增或更新当前有效差异，在第五节预登记变更；载体必须指向仓库文件、commit、迁移版本或 BPMN key/version，不能只写“服务器已改”。
5. 普通 push 会部署双机。若功能只应在一机生效，提交前必须确认另一机有可靠的配置、模块或租户守卫；不可寄望于“另一机暂时没有这条数据”。

### 变更后

1. 分别核验两机运行 commit/产物及健康状态；目标专属变更还须验证非目标机未生效。
2. 使用目标环境真实接口与真实数据验收；不以 mock、空数据或另一机结果替代。
3. 将验证时间、报告/脚本路径、关键结果和回滚方式写入第五节，并同步第四节的当前状态。
4. 若验证受阻，状态保留为“已实施待验证”，按项目测试受阻规则登记；禁止写成“已验证”。
